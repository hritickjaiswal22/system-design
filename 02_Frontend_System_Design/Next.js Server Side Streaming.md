# RSC Payload

The React Server Component (RSC) Payload is a compact, serialized data format generated by the server that represents the rendered React Server Components tree. It acts as the operational bridge between server-side data fetching and client-side UI rendering in the Next.js App Router.

### What is Inside the RSC Payload?

The payload does not contain raw JavaScript application logic. Instead, it contains instructions and data structured for React to reconstruct the DOM:

- Rendered Output: The final HTML-like structure of all Server Components.
- Client Placeholders: Dedicated indicators marking exactly where Client Components must be placed.
- Module References: Precise file links to the compiled JavaScript chunks needed to load those Client Components.
- Serialized Props: Any data or props explicitly passed from a Server Component down to a Client Component.

### How Next.js Uses the Payload

The lifecycle of the RSC payload changes depending on how a user interacts with your application:

`[Initial Request] ──> Server renders RSC Tree ──> Generates RSC Payload ──> Prerenders Static HTML ──> Sent to Browser`

`[Navigation] ──> Browser requests data ──> Server returns RSC Payload only (No HTML) ──> React updates DOM`

#### 1. On Initial Page Load

- Step A: The server processes your route and renders the Server Components into the RSC Payload.
- Step B: Next.js uses this payload combined with Client Component instructions to compile a raw, static HTML preview.
- Step C: The browser receives the static HTML first for an instantaneous visual preview. Simultaneously, the RSC payload is streamed into the background so React can align the static layout with the interactive Client Components (Hydration).

#### 2. On Subsequent Navigations (SPA Mode)

- When a user clicks a link to change pages, Next.js does not fetch a new HTML file.
- Instead, it performs a lightweight fetch request targeted directly at the new route's RSC Payload.
- React client-side code parses this payload, updates the browser DOM on the fly, and maintains client state like input values or focus points.

Also note client can request for re-trigger of a Server Component’s output causing to send new RSC payload which can then merged to show changes via `server actions`

### How to Inspect the Payload

You can view this data passing through your network log:

1. Open your browser Developer Tools (F12) and select the Network tab.
2. Filter the requests by Fetch/XHR.
3. Click links or refresh a page within your Next.js application.
4. Look for requests containing `_rsc` query parameters or responses matching `text/x-component` the content type. The data will look like an optimized, stringified stream of arrays and objects containing layout directions.

### Important Optimization Rules

- Keep Props Serializable: You can only pass data across the Server-Client boundary that can be formatted to JSON (strings, numbers, arrays, plain objects, or Promises). You cannot pass functions or complex class instances.
- Watch the Payload Size: If you fetch massive database objects in a Server Component and pass them directly as props to a Client Component, your entire raw dataset gets injected into the RSC payload. Only forward the specific fields your Client Component needs to render to keep your network footprint small.

# One Small Misconception

This sentence:

> HTML sent to client with parallel RSC payload streaming

People often think HTML and Flight are literally sent as two completely independent downloads.

A better mental model is:

```
Server

↓

HTML stream

↓

Embedded references to Flight data

↓

Flight chunks

↓

Client reconstructs tree
```

The browser receives HTML progressively while React simultaneously receives Flight chunks.

They're coordinated rather than being two unrelated network requests.
